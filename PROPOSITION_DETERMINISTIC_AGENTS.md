# Proposition: Deterministic HTTP Agents for Integration Testing

## Status

Draft implementation plan. Awaiting approval before code changes.

---

## Problem

The architecture has a powerful test seam (HTTP boundary + text-only agents) but no harness to exploit it. Running the pipeline currently requires:
1. Real LLM agents (expensive, slow, non-deterministic)
2. Real EventStoreDB (requires setup)
3. Real VM workers (requires Vast.ai)
4. Human operator intervention

We need a way to exercise the full pipeline — parser, handler, event store, projections — without LLM calls, VM provisioning, or human input.

---

## Solution: Deterministic HTTP Agents

A **deterministic HTTP agent** is a real FastAPI service that implements `GET /` and `POST /`. It returns natural language text. The system cannot distinguish it from an LLM agent because the architecture forbids inspecting anything beyond the text.

### What It Is

- A real HTTP service with real routes
- Returns text, not JSON effects
- The real parser extracts effects from its text
- The real handler appends to EventStoreDB
- The real projections update

### What It Is Not

- Not a mock (it does not bypass handler/parser/event store)
- Not a test double (it does not replace production code)
- Not a stub (it does not return hardcoded responses to specific inputs)
- Not a simulation (it exercises real code, not a model of real code)

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                     Test Orchestrator                       │
│  (pytest test case, shell script, or manual invocation)     │
└──────────────┬──────────────────────────────────────────────┘
               │
               │ 1. Spawns Deterministic Agents
               │ 2. Spawns GSA
               │ 3. Waits for pipeline completion
               │ 4. Reads EventStoreDB, asserts
               ▼
┌─────────────────────────────────────────────────────────────┐
│              Deterministic Agent (port 9001)                │
│                                                             │
│  GET  /  →  Returns empty (no state to expose)             │
│  POST /  →  Reads config → Returns next text in sequence   │
│                                                             │
│  Config: /tmp/test-agents/scenario.yaml                     │
│    turn_0: "Starting pipeline. Budget $10. Config default." │
│    turn_1: "Scene 1 narration: 'In 1924...' Duration 30s." │
│    turn_2: "No more scenes needed."                         │
└──────────────┬──────────────────────────────────────────────┘
               │ text (natural language)
               ▼
┌─────────────────────────────────────────────────────────────┐
│                 Scenario Agent Handler                      │
│                 (REAL production code)                      │
│  POST / receives text → parser extracts effects →          │
│  append to EventStoreDB                                     │
└──────────────┬──────────────────────────────────────────────┘
               │ effects
               ▼
┌─────────────────────────────────────────────────────────────┐
│                   EventStoreDB                              │
│              (test container or embedded)                   │
└──────────────┬──────────────────────────────────────────────┘
               │ events
               ▼
┌─────────────────────────────────────────────────────────────┐
│              GSA (Global State Agent)                       │
│              (REAL production code)                         │
│  subscribes to ESDB → rebuilds projections →               │
│  GET / returns GlobalStateResponse                          │
└─────────────────────────────────────────────────────────────┘
```

The deterministic agent is just another agent in the topology. It POSTs to other agents. Other agents POST to it. The only difference: its text is authored by a human test designer, not generated by an LLM.

## Configuration Format

Deterministic agents are configured via YAML files that declare what text to emit on each turn. Two modes: **sequence mode** and **state-driven mode**.

### Sequence Mode

Emit text in a fixed order, regardless of input:

```yaml
# /tmp/test-agents/scenario.yaml
agent: scenario
port: 9001
mode: sequence
turns:
  - text: |
      Starting pipeline for run {run_id}. Budget $10.00.
      Max attempts per block: 5. Output path: /tmp/final.mp4.
  - text: |
      Scene 1, V1 Hook narration: "In 1924, the world stood at a crossroads."
      V2 Expert narration: "The Dawes Plan of 1924 restructured German reparations."
      V3 Storyteller narration: "Imagine a banker in 1924, staring at ledgers..."
      Visual notes: Close-up of ledger pages, archival footage of Berlin.
      Dopamine hook: "What if the entire world economy depended on one man's signature?"
      Duration: 30 seconds.
  - text: |
      Scene 2, V1 Hook narration: "Then came the crash."
      V2 Expert narration: "Black Tuesday, October 29, 1929."
      V3 Storyteller narration: "The ticker tape machines could not keep up."
      Visual notes: Slow-motion ticker tape, panicked traders.
      Dopamine hook: "In 24 hours, $14 billion vanished."
      Duration: 25 seconds.
  - text: |
      All scenes complete. Script finalized.
```

### State-Driven Mode

Emit text based on GSA projection state. The agent queries GSA via `GET /?run_id={run_id}` on every turn:

```yaml
# /tmp/test-agents/audio.yaml
agent: audio
port: 9002
mode: state-driven
gsa_url: http://localhost:8000
rules:
  - condition: |
      pipeline_started exists and reconciliation_complete is false
      and dirty_blocks contains "A1:1:1"
    text: |
      Block A1:1:1 needs TTS generation.
      Voice: V1. Text: "In 1924, the world stood at a crossroads."
      Queuing TTS job for scene 1, phrase 1.
  - condition: |
      pipeline_started exists and reconciliation_complete is false
      and dirty_blocks is empty and clean_blocks contains "A1:1:1"
    text: |
      All audio blocks verified. Reconciliation complete.
      Duration matched within tolerance. Proceeding to video.
  - condition: |
      pipeline_started exists and reconciliation_complete is true
    text: |
      Audio phase done. Nothing to do.
      NoOp.
```

### Pipeline Driver Mode

A special deterministic agent that reads the full GSA state and decides which agent to wake next. It does not replace any production agent — it sits outside the pipeline and drives it:

```yaml
# /tmp/test-agents/driver.yaml
agent: driver
mode: pipeline-driver
gsa_url: http://localhost:8000
agents:
  scenario: http://localhost:8001
  audio: http://localhost:8002
  video: http://localhost:8003
  assembly: http://localhost:8005
  provisioner: http://localhost:8081
rules:
  - condition: "no PipelineStarted"
    action: post_to scenario with text "Start pipeline for topic '1920s economy'"
  - condition: "PipelineStarted exists and OTIO has unfilled A1 slots"
    action: post_to scenario with text "Continue script writing"
  - condition: "OTIO has dirty audio blocks"
    action: post_to audio with text "Wake for reconciliation"
  - condition: "All audio clean and V1 slots unfilled"
    action: post_to video with text "Wake for video production"
  - condition: "All slots filled and no PipelineComplete"
    action: post_to assembly with text "Wake for final assembly"
  - condition: "PipelineComplete exists"
    action: terminate
```

## What Production Code Changes?

**None.** The deterministic agent is a new directory (`test_agents/`) that imports production modules (`effects.py`, `event_store.py`) but does not modify them. The production agents remain untouched.

The only touch point: production agents must be startable on configurable ports. This is already true (agents accept `port` parameter or read from config).

---

## What About the Parser?

The parser calls instructor → deepseek-v4-flash. This is slow (~500ms/turn) and costs tokens. For CI, we want deterministic tests to be fast.

**Solution:** The deterministic agent's text is authored to be unambiguous. The parser with instructor at temperature=0.0 extracts the correct effect on the first try, no reasking. The latency is the cost of testing the real parser.

**No parser bypass.** The parser is production code. Testing without it would be a mock.

**Future optimization:** If CI latency becomes unacceptable, we can add a `--parser-deterministic` flag that uses a local model (e.g., `deepseek-v4-flash` via local inference) instead of the API. This is still a real model, not a mock.

## Example Test

```python
# tests/test_full_pipeline.py
import pytest
from test_harness import PipelineTestHarness


def test_full_pipeline():
    harness = PipelineTestHarness()
    
    # Start test infrastructure
    harness.start_event_store()
    harness.start_gsa()
    
    # Spawn deterministic agents
    harness.spawn_agent("scenario", "test_agents/configs/full_pipeline_scenario.yaml")
    harness.spawn_agent("audio", "test_agents/configs/full_pipeline_audio.yaml")
    harness.spawn_agent("video", "test_agents/configs/full_pipeline_video.yaml")
    harness.spawn_agent("assembly", "test_agents/configs/full_pipeline_assembly.yaml")
    harness.spawn_agent("provisioner", "test_agents/configs/full_pipeline_provisioner.yaml")
    
    # Driver orchestrates the pipeline
    harness.run_driver("test_agents/configs/full_pipeline_driver.yaml")
    
    # Assert on event sequence
    events = harness.read_events("test-run-001")
    assert_event_kinds(events, [
        "pipeline_started",
        "budget_set",
        "update_script",
        "update_script",
        "queue_job",
        "vm_allocated",
        "job_started",
        "job_completed",
        "audio_generated",
        "audio_measured",
        "reconciliation_complete",
        "merge_into_otio",
        "pipeline_complete",
    ])
    
    # Assert on final projections
    gsa = harness.get_gsa_state("test-run-001")
    assert gsa.otio_projection.all_slots_filled()
    assert gsa.budget_projection.remaining_usd() > 0
    assert gsa.state_projection.current_phase == "done"
```

## Open Questions

1. **Should the driver agent be a separate process or a thread in the test harness?**
   - Separate process: mirrors production (agents are separate)
   - Thread in harness: simpler, but not a real HTTP service
   - Recommendation: separate process. The architecture says agents are HTTP services.

2. **How do we handle the Provisioner's bash tool?**
   - The Provisioner deterministic agent emits text like "Executed: vastai create instance ..."
   - The handler runs the real bash command
   - For tests without Vast.ai, the Provisioner agent could emit text describing the expected outcome
   - Or we skip Provisioner tests and test VM effects via direct handler injection
   - Recommendation: Provisioner deterministic agent emits text describing VM operations. Handler executes bash. Tests without Vast.ai use `--skip-provisioner` flag.

3. **Should we support multi-run tests?**
   - Yes. The harness can spawn 10 deterministic agents across 10 run_ids and assert they all complete independently.
   - This tests per-run_id isolation and GSA subscription correctness.
