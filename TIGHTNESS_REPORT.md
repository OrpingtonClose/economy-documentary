# V7 Architecture TIGHTNESS Assessment

> Generated by cross-referencing §3 effect definitions, §6 projection handlers, §9.5 parser spec, Diagram 4 (Effect Family Graph), Diagram 12 (Component Matrix), Diagram 13 (Bootstrap), and server/effects.py / server/effect_parser.py.

## Executive Summary

**VERDICT: NOT TIGHT.** 14 distinct categories of inconsistency found across spec, diagrams, and code. The spec defines 32 effect types with rigorous field contracts, but the implementation (server/effects.py + effect_parser.py) only covers 18, with different field names, different discriminant fields, and a completely different base model. The spec itself contains one phantom effect (`CostIncurred`) referenced in a projection handler but never defined, and two effects (`PipelineAborted`, `DeleteFromOTIO`) missing producer arrows in Diagram 4.

## Category B: Spec Internal Inconsistencies (MAJOR)

### B.1 Phantom effect: `CostIncurred`

**Location:** §6.5 BudgetProjection handler, line 2828 and 2852.

The `BudgetProjection.apply()` has a `case "cost_incurred":` branch, but **no `CostIncurred` effect is defined anywhere in §3**. The spec says:

> "All subsequent VM costs are accumulated via CostIncurred events emitted by the Provisioner when VMs are deallocated."

But `VMDeallocated` (§3.5.2) already carries `final_cost` and `runtime_sec`. There is no separate `CostIncurred` effect in `EffectUnion`, `KIND_TO_MODEL`, or any diagram.

**Fix:** Either define `CostIncurred` in §3 as a proper effect, or change `BudgetProjection` to derive cost from `VMDeallocated.final_cost`.

### B.2 Field name mismatch: `budget_usd` vs `budget_cap_usd`

**Location:** §3.7.2 `BudgetSet` defines `budget_usd: float`, but §6.5 `BudgetProjection` handler reads `event.budget_cap_usd`.

**Fix:** Align the field name. Either rename `BudgetSet.budget_usd` → `budget_cap_usd`, or change the projection handler to read `budget_usd`.

### B.3 9 effects have no projection handler

These effects are defined in §3 but never appear in any `match event.kind:` case statement across all projection handlers:

| Effect | Defined in §3 | Handled by projection? | Notes |
|---|---|---|---|
| `agent_loop_detected` | §3.8.2 | NO | Explicitly documented as "no projection applies it" — OK |
| `audio_generated` | §3.4.1 | NO | Produced by VM worker; should update OTIO or Job state |
| `audio_measured` | §3.4.1 | NO | Used for reconciliation; should update OTIO or Job state |
| `clarification_request` | §3.8.1 | NO | Routing effect; may not need projection — OK |
| `execute_raw_bash` | §3.8.3 | NO | Action effect; may not need projection — OK |
| `human_instruction` | §3.8.1 | NO | Routing effect; may not need projection — OK |
| `job_approved` | §3.3.3 | NO | Should update JobProjection state |
| `noop` | §3.8.2 | NO | Explicitly documented as "passes through untouched" — OK |
| `vast_global_state_observed` | §3.7.1 | NO | Should update a global-state projection |

**Fix:** Add projection handlers for `audio_generated`, `audio_measured`, `job_approved`, and `vast_global_state_observed`. The others are intentionally projection-less.

## Category D: Naming Convention Violations (MEDIUM)

### D.1 `QueueJob` vs `JobQueued`

Spec uses `QueueJob` (imperative, agent request). Code uses `JobQueued` (past tense, system outcome). The spec's naming convention (§3.10.3) says imperative for agent requests, but `QueueJob` is produced by agents (Audio/Video), so imperative is correct. The code's `JobQueued` follows a different convention.

### D.2 `AudioGenerated` vs `GenerateNarrationAudio`

Spec: `AudioGenerated` (past tense, system outcome — correct per convention).
Code: `GenerateNarrationAudio` (imperative, agent request — but it's produced by VM worker, not agent).

### D.3 `JobApproved` vs `QAPassed`/`QAFailed`

Spec has single `JobApproved` effect. Code splits into `QAPassed` and `QAFailed`. The spec's `JobApproved` has `quality_notes` and `reviewed_by` fields; the code's `QAFailed` has `comments` and `suggested_fix`.

**Location:** §6.3 JobProjection, lines 2549-2554.

```python
case "production_failed":
    self.production_failures.append({
        "slot_id": getattr(event, "slot_id", ""),
        "failure_type": getattr(event, "failure_type", ""),
```
