# HTTP Boundary as Test Seam — Architectural Assessment

## Core Thesis

The uniform `GET /` + `POST /` HTTP surface across every agent creates a **natural test seam** at the network boundary. Any HTTP-speaking process that implements these two endpoints is indistinguishable from a production agent. This is not a side effect — it is a **first-class testing primitive** that emerges directly from the architecture.

---

## What the Seam Enables

### 1. Deterministic Agent Replacements

A real HTTP service (not a mock) implements `GET /` and `POST /`. On `POST /`, it returns deterministic natural language text — the same text every time, generated by deterministic code, not an LLM. The parser extracts effects from this text exactly as it would from an LLM agent. The handler, EventStoreDB, and projections all fire with real production code.

The difference from a mock: this is a real HTTP service. It speaks HTTP. It returns text. The system cannot tell it apart from an LLM agent because the architecture explicitly forbids the system from inspecting anything beyond the text.

### 2. Recorded Replay

Capture a real agent's HTTP interactions during a manual run: the text it emitted, the GSA state it read, the downstream agents it woke. Store this as a timeline. Replay by spawning deterministic HTTP services that return the recorded text responses in sequence.

The event store should match the original run (deterministic because temperature=0.0 and projections are pure folds). Any divergence indicates a regression in parser, handler, or projection logic.

### 3. Pipeline Drivers

A deterministic HTTP service that reads GSA state via `GET /` and decides what text to emit based on that state. It can drive the pipeline through emergent phases automatically:
- Sees no `PipelineStarted` → emits text describing pipeline start
- Sees unfilled script slots → emits narration text
- Sees dirty audio blocks → emits queue job text
- Sees all slots filled → emits assembly text

This is a **real agent** by architecture definition. It just happens to be deterministic.

### 4. Resilience Testing

A deterministic HTTP service that emits edge-case text: empty, too short, vague, contradictory, malformed. The parser and handler must handle it without crashing. The projections must remain consistent. This tests the error paths of the real system, not a mocked version.

### 5. Concurrency Testing

Spawn many deterministic HTTP services, each assigned a different `run_id`, all POSTing simultaneously. Tests per-run_id asyncio.Lock, EventStoreDB concurrent append, GSA subscription throughput, and projection correctness under load. No LLM calls = fast enough for CI.

---

## The Invariant That Makes This Possible

> **Principle:** Only `GET /` and `POST /` everywhere.

If agents had gRPC, WebSockets, shared memory, or direct function calls, the seam would require protocol-specific replacements. HTTP means any HTTP-speaking service is a valid agent.

> **Principle:** Agents produce natural language text only.

A deterministic service emits text. An LLM agent emits text. The system cannot tell them apart. If agents emitted binary protobuf or structured JSON, replacements would need to know the schema — coupling tests to implementation.

> **Principle:** No state machine, no enforced transitions.

A deterministic service can emit `PipelineComplete` on turn 1 and the system handles it (as a `NoOp` or error). No framework rejects "invalid" sequences. Replacements don't fight a state machine.

---

## Caveats and Trade-offs

### A. Parser calls instructor → LLM on every turn

Deterministic text → deterministic effects only if the parser is deterministic. Instructor + deepseek-v4-flash at temperature 0.0 is *mostly* deterministic but not guaranteed. A 50-turn test takes ~25 seconds due to LLM latency.

**Implication:** Full replay tests with the real parser are integration tests, not unit tests. They are valuable but slow.

### B. Temperature=0.0 is not perfectly deterministic

Instructor reasking paths, retry behavior, and model updates can cause divergence. Recorded replays may not match exactly on re-runs.

**Implication:** Replay tests assert on approximate event sequences, not bit-exact matches. Or they run with max_retries=0 to eliminate reasking variability.

### C. Agent system prompts are not exercised

A deterministic replacement doesn't have a system prompt. It won't respect "maximum 15 tool calls" or "check resource existence before creating." Tests of prompt-level rules require real LLM agents.

**Implication:** Deterministic replacements test *pipeline mechanics* (handler, parser, event store, projections). Real LLM agents test *agent reasoning* (prompt adherence, planning, error recovery). These are separate test concerns.

### D. GSA state is shared across runs

Multiple replacements reading GSA concurrently don't interfere because each queries with `run_id=xxx`. The architecture already isolates runs.

**This is a feature.** Tests exercise the real concurrency model without special test infrastructure.

## Test Taxonomy

| Test Type | Agent | Parser | EventStoreDB | Speed | What It Tests |
|---|---|---|---|---|---|
| Handler logic | Deterministic HTTP service | Real instructor | Test container | ~500ms/turn | Handler routing, projection updates |
| Full pipeline flow | State-driven deterministic service | Real instructor | Test container | ~10s/run | Emergent phase transitions |
| Regression replay | Recorded-response deterministic service | Real instructor | Test container | Matches recording | Behavioral stability across commits |
| Concurrency | Many deterministic services | Real instructor | Test container | ~1000 req/s | Lock contention, subscription throughput |
| Resilience | Edge-case deterministic service | Real instructor | Test container | Variable | Parser/handler error handling |
| Agent reasoning | Real LLM agent | Real instructor | Test container | ~30s/run | Prompt adherence, planning quality |

## What the Architecture Gets Right

1. **HTTP everywhere** = universal replacement boundary
2. **Text-only agent output** = replacements are trivial to build (any HTTP service that returns text)
3. **No state machine** = replacements don't fight enforced transitions
4. **Event sourcing** = test assertions are simple event sequence checks
5. **Parser as sole bridge** = the only component that needs to handle deterministic text
6. **Per-run_id isolation** = parallel tests without interference

## What Could Be Added

1. **Deterministic agent harness** — a documented, first-class HTTP service in the repo that can be configured to emit specific text sequences. Not a mock — a real HTTP service that happens to be deterministic.
2. **Event sequence assertion library** — `assert_events(run_id, ["PipelineStarted", "BudgetSet", "UpdateScript", ...])` — reads EventStoreDB and verifies.
3. **GSA snapshot capture** — record GSA responses at each turn for deterministic replay
4. **Parser determinism mode** — a configuration that pins instructor to exact reproducible behavior (fixed seed, no reasking, known model version)

---

## Verdict

**The HTTP boundary is the most valuable test seam in the architecture.** It was not designed for testing, but the constraint "only GET / and POST / everywhere" accidentally created a perfect testing primitive. Replacements are trivial because agents are text-only. The system under test is everything except the agent itself — and the agent is the easiest part to replace.

**Recommendation:** Do not add dedicated test interfaces. The existing HTTP surface is the interface. Invest in deterministic HTTP services that exercise the real parser, handler, event store, and projections. Do not build mocks or test doubles that bypass production code.
